## State machine (as built)

`select → trust_gate → installing → collecting → staging → validating → granting → done | failed`

- **select** — `kind: noop`, null-safe projection of the input `candidate`
  into flat context fields (`name`, `transport`, `trust_tier`,
  `secrets_required`, `config_required`, `npmPkg`, `sourceUrl`, …).
- **trust_gate** — exhaustive 3-way split over the closed `TrustTier` set:
  `proceed_verified` / `proceed_org` → `installing`; `reject_community` →
  `failed` (`COMMUNITY_REQUIRES_PHASE3`); `reject_unknown_tier` (the
  complement of the other two, not a bare unguarded fallback) → `failed`
  (`UNKNOWN_TRUST_TIER`).
- **installing** — `kind: cli`, `treatNonZeroAsFailure: false` +
  `branches` (not executor-error) decides the route, so a bad exit lands a
  real `INSTALL_FAILED` reason in `failed` rather than rejecting the
  submit. Covers `stdio`+npm (`npm install -g <pkg>`) and `remote`/`rest`
  (nothing to install, `kind: noop`); anything else →
  `INSTALL_RECIPE_UNAVAILABLE`.
- **collecting** — `actor: human`, elicits `requires.secrets` (recorded as
  env-var **names**, never values) + `requires.config`. Deliberately a
  **pull-only** gate (see limitation below).
- **staging** — `kind: cli` → `praxec connections add` (STAGE, inert).
  Covers the three transports the design doc names: `stdio`+npm (mcp +
  command), `remote` (mcp + url), `rest` (rest + url). Same
  branches-decide-the-route pattern; `STAGE_FAILED` / `STAGE_RECIPE_UNAVAILABLE`.
- **validating** — `kind: cli` → `praxec doctor --config …` (P2.1's
  `required_secrets` check). `VALIDATION_FAILED` on non-zero — nothing
  granted yet.
- **granting** — THE operator trust act. `approve_grant` (`actor: human`,
  `permission: workflow.approve`) → `kind: cli` → `praxec connections
  grant --config … <name> --yes`; the `--yes` is safe here specifically
  because the workflow's own human-gate approval *is* the proven operator
  origin. `decline_grant` never touches the CLI. `GRANT_FAILED` /
  `OPERATOR_DECLINED`.
- **done** / **failed** — terminal. `done`'s `onEnter` sets
  `wired: true`, `connection_name`, clears `reason`. `failed` carries
  whatever `reason` the arriving transition set.

## The grammar-limitation finding (as instructed, reporting rather than faking)

Confirmed by reading `crates/praxec-executors/src/cli.rs` +
`crates/praxec-executors/src/arg_render.rs`:

- `args:` on a `kind: cli` step is a **static** JSON array. Each element is
  independently resolved to exactly **one** argv token
  (`render_arg`/`read_in_scopes`): either a whole-value path read
  (`$.context.foo`) or a literal. There is no loop/spread/`argsFrom`
  construct that expands one array-valued context field into N argv
  tokens, and no string-interpolation inside a single token — a mixed
  literal+path string like `"--env=$.context.x"` is NOT templated; it
  either matches a known scope prefix in full or is a plain literal.
- Guard `expr` (`crates/praxec-core/src/guards.rs`) and output-mapping
  operators (`crates/praxec-core/src/mapping.rs`: `add|subtract|multiply|
  divide|set|concat|pick`) have **no `length()`/count function**, so you
  also can't statically branch on "how many secrets does this candidate
  declare" without a real code component.

Net effect: `connections add --env NAME=VALUE` (or `--arg`) can be
composed for a **fixed, known-at-authoring-time** number of flags (which
is what `staging` does for the connection identity — `--command`/`--url`/
the two `-y <pkg>` npx args), but **not** for the arbitrary-length
`requires.secrets`/`requires.config` a Phase-1 registry candidate may
declare. `collecting` still elicits and records these fully (JSON has no
such arity limit — only CLI argv does), so the operator-facing behavior
and the audit trail (`secrets_set`) are complete; only the *automatic
wiring of those secrets into the staged connection's `env:` block* is out
of scope for this reference implementation. Closing that needs either (a)
a core `add_connection`-with-JSON-requires primitive (the design doc's own
§8 "Option A"), or (b) a new `argsFrom`/spread capability on the `cli`
executor. I did not invent either — flagging per your instruction so you
can re-scope P2.2/P2.3 if this blocks something.

No other grammar limitation was hit — `[*]` array-projection
(`$.context.secretEnvNames[*].envVar`) and the `concat` output operator
both exist and were usable (I ended up not needing `concat` once I
dropped per-secret env wiring from `staging`, but it's real and would help
a future fixed-arity extension).

## Verify

1. `cargo run -q -p praxec -- check --config examples/tool-provision/gateway.yaml`
   → **0 errors**, 2 warnings:
   - `ELICITATION_INCOMPATIBLE_GATE` (V36) on `collecting.submit_collection`
     — expected/documented: this is intentionally a pull-only human gate
     (free-form env-var mapping, no finite pick-list fits `choices:`); V36
     is a Warning specifically because "pull-only object gates are
     legitimate" (see the test `v36_is_silent_on_remediated_fixture_gates`
     and the docstring on `validate_human_gate_elicitation` in
     `crates/praxec-core/src/validate.rs`).
   - `EPHEMERAL_STORAGE` — the standard dev-config warning every
     stderr-sink/memory-store example gets; cosmetic for a reference config.
2. `cargo run -q -p praxec -- fuzz --config examples/tool-provision/gateway.yaml`
   → smoke: **1 def(s) ok**, no Wedge/Livelock/EngineError anywhere in the
   run. Per-edge coverage: 20/23 edges ✓. The 3 uncovered edges are all
   `granting.approve_grant`/`granting.decline_grant` — both guarded by
   `kind: permission`. This is the exact same residual as the shipped
   `examples/expense-approval` (its 7 permission/role-guarded human edges
   show identically as "could not satisfy guard (evidence/role?)"): the
   fuzz harness's static satisfier
   (`crates/praxec-test/src/analysis/reads.rs::all_guard_exprs`) only
   derives a satisfying value for a top-level `kind: expr` guard — it
   doesn't attempt `permission`/`role`/`evidence` (or, initially, composite
   `any_of`/`all_of` — I refactored `trust_gate.proceed_trusted` and
   `installing.install_not_needed` from one `any_of`-guarded transition
   each into two flat single-`expr` transitions specifically so the
   satisfier could cover them; that fix landed clean, 20/23 → all
   non-permission edges now ✓). The overall `fuzz` process still exits
   non-zero ("fuzz found coverage failures") purely because of these 2
   permission-guarded edges — identical to what `expense-approval`
   produces today. Not a defect in this workflow; a known, precedented
   harness limitation for permission-gated HITL gates.
