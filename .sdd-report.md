## What shipped

### (a) CLI: `connections add --block <json>`
- `crates/praxec-executors/src/conn_write.rs`: new `add_connection_raw(config, name, block_json)`.
  Parses the JSON, validates it is an object with a recognized `kind` (mcp|cli|rest via
  the existing `ConnectionKind::parse` poka-yoke), then stages it through a newly-extracted
  `stage_entry()` — the SAME write tail `add_connection` (flag form) now uses: same
  duplicate-name check, same `stagedConnections:` block, never grants. New typed error
  `ConnWriteError::InvalidBlock`.
- `crates/praxec/src/gateway_config.rs`: `ConnectionsCommand::Add` — `kind` is now
  `Option<CliConnectionKind>`, added `block: Option<String>`. Doc comments spell out
  precedence (`--block` wins; `--kind`/`--command`/… ignored when `--block` present) and
  that either `--block` or `--kind` is required.
- `crates/praxec/src/gateway.rs`: `connections_add` takes `block`; `--block` path stages
  raw, else the unchanged flag→`ConnectionSpec` path. Flag form works exactly as before.
- Tests (`conn_write.rs` unit + `tests/connections_cli.rs` integration):
  `--block` stages whole body incl. arbitrary-length env map; duplicate-name still errors;
  invalid-JSON / non-object / missing-kind / unknown-kind all fail typed; add-with-neither
  `--block`-nor-`--kind` exits non-zero. Existing tests untouched and green.

### (b) Flow: `flow.tools.provision.yaml`
- New `building` state between `collecting` and `staging`. A `kind: script` step
  (`build.connection-body`, jq — declared in the flow's own colocated `scripts:` block)
  reads `secretEnvNames` + `collectedConfig` (both arbitrary-length JSON, not CLI argv)
  and emits ONE JSON connection body into the `built_body` context slot. Transport guards
  (stdio/remote/rest) mirror `installing`, checked before the script spawns;
  `build_unsupported` → `BUILD_RECIPE_UNAVAILABLE`.
- `staging` collapsed from 3 kind-guarded `connections add` calls to ONE ungated
  `connections add --config … --name … --block "$.context.built_body"` — `built_body`
  already carries the resolved kind, and `render_arg`'s whole-value-path fallback
  (`other.to_string()`) compact-serializes the object slot to a single argv token.
- Secrets vs config wired **differently, on purpose**:
  - `requires.config` (non-secret) → literal `env:` entries.
  - `requires.secrets` → `required_secrets:` NAMES only, never values. The real secret
    reaches the spawned child via the operator's inherited process environment
    (`std::process::Command` inherits parent env — `cli.rs`/`mcp.rs`), so nothing here
    ever holds secret material. Writing a `"$NAME"` placeholder into `env:` would be
    *wrong* — `cmd.env(k,v)` sets it verbatim and would SHADOW the correctly-inherited
    real secret. Documented at length in the flow header + README.
  - REST candidates get identity only (no child process to inherit into; `restConnection`
    has no `env:`/`required_secrets:`), so secrets/config are not silently dropped.
- Header comment + `examples/tool-provision/README.md` + `gateway.yaml` updated: the
  documented grammar-limit gap is now CLOSED, honestly explaining the limit still exists
  (`cli` args are still a static array) but is bypassed by doing the arity work in a real
  interpreter (`building`'s script), not in the arg grammar. `jq` added as a runtime dep.

### Latent P2.1 gap fixed (dependency of the above)
`required_secrets` was read by `praxec doctor`/`preflight.rs` (P2.1, #169) but was **absent
from `mcpConnection` in `schemas/gateway-config.schema.json`** (`additionalProperties:false`).
So granting ANY connection that declared it failed `INVALID_STAGED_CONNECTION` at load —
the P2.1 feature was silently ungrantable, and P2.3b needs it to ride in a `--block` body.
Added the `required_secrets` array property (+ the byte-identical packaged copy in
`crates/praxec-schema/schemas/`, kept in sync per `schema_sync` test) and a regression test
`add_block_with_required_secrets_stages_and_grants`.

  not introduced here.
